# Web Push, explained from scratch

Working notes on how push notifications actually work, and how this repo implements them. Written for someone who has never touched the Push API, VAPID, or the RFCs.

Read the [Glossary](#glossary) first if a term stops you — everything is defined there.

---

## 1. The problem push solves

A web page can only make things happen while it's open. Close the tab, and your JavaScript is gone. So how does a notification arrive on your phone three hours later, when the app isn't running?

It doesn't come from your server directly. **Your server cannot reach your phone.** Your phone has no public address, it's behind carrier NAT, its IP changes, and it's asleep most of the time.

Instead, every browser vendor runs a **push service** — a server that phones maintain a persistent connection to:

- Apple devices → `web.push.apple.com`
- Chrome → `fcm.googleapis.com`
- Firefox → `updates.push.services.mozilla.com`

The phone holds one battery-efficient connection to its vendor's push service. Your server sends a message *to that push service*, and the push service relays it down the existing connection.

```
your Worker  ──HTTPS POST──>  Apple's push service  ──existing connection──>  your iPhone
                                                                                   │
                                                                          wakes the service worker
                                                                                   │
                                                                          shows the notification
```

Three consequences fall out of this, and they explain nearly every design decision that follows:

1. **You need a service worker.** The page is closed, so there's no page to receive the message. A service worker is a script the browser can wake up without any page open. This is *why* push requires one — not an arbitrary rule.
2. **A third party is in the middle.** Apple relays your message. So the message gets encrypted end-to-end, and Apple can't read it.
3. **The push service needs to know who you are.** Otherwise anyone who learned an endpoint URL could spam it. That's what VAPID is for.

## 2. The subscription

Before anything can be sent, the browser has to create a **subscription**. This happens once per device, in the page, after the user grants permission:

```js
const subscription = await registration.pushManager.subscribe({
  userVisibleOnly: true,
  applicationServerKey: <your VAPID public key>,
});
```

What comes back is three pieces of data:

```json
{
  "endpoint": "https://web.push.apple.com/QF9x...long-opaque-string",
  "keys": {
    "p256dh": "BEl62i...",
    "auth": "8eDyX_uCN0X..."
  }
}
```

| Field | What it is |
|---|---|
| `endpoint` | The URL **you POST to** in order to reach this one device. Generated by the push service. Treat it as a secret — anyone holding it can send to that device (subject to VAPID). |
| `p256dh` | The device's **public key**. You'll use it to encrypt. The device holds the matching private key, which never leaves it. |
| `auth` | A 16-byte random shared secret, mixed into the encryption. Not a key on its own. |

Your server stores all three. In this repo that's the `push_subscriptions` table — one row per device.

**The endpoint is the address, the keys are the lock.** Sending a push means: POST encrypted bytes to `endpoint`, encrypted using `p256dh` + `auth`.

### `userVisibleOnly: true`

You must promise to show a visible notification for every push you receive. Browsers enforce this — if your service worker receives a push and *doesn't* call `showNotification`, the browser may show a generic "This site was updated in the background" notification, and repeated offences can cost you push permission entirely.

This is why `sw.js` in this repo always shows *something*, even if the payload fails to parse.

## 3. VAPID — proving who you are

**VAPID** = Voluntary Application Server Identification. RFC 8292.

The problem: push endpoints are just URLs. If one leaked, anyone could POST to it. VAPID makes the push service check that a message came from *you*.

It's public-key cryptography, which if you haven't used it works like this: you generate a **pair** of mathematically linked keys. The **private key** signs things. The **public key** verifies those signatures but cannot produce them. You give the public key away freely and guard the private one.

The flow:

1. You generate one VAPID keypair, once, ever. (`npm run generate:vapid`)
2. The **public** key gets handed to the browser when subscribing (`applicationServerKey` above). The push service records it against that subscription.
3. Every time you send, you attach a short-lived **JWT** signed with your **private** key.
4. The push service verifies that signature against the public key it recorded. Mismatch → rejected.

The JWT is three base64url chunks joined by dots — `header.payload.signature`:

```json
// header
{ "typ": "JWT", "alg": "ES256" }

// payload
{
  "aud": "https://web.push.apple.com",   // ORIGIN ONLY — see below
  "exp": 1787819999,                      // expires within 24h
  "sub": "mailto:george@hearvie.dev"      // how the push service contacts you
}
```

Three things bite people here, all of which this repo handles explicitly:

**`aud` must be the origin, not the full endpoint.** The endpoint is `https://web.push.apple.com/QF9x.../long/path`, but `aud` must be exactly `https://web.push.apple.com`. Include the path and every push service rejects the token. In `crypto.ts`: `new URL(endpoint).origin`.

**`ES256` signatures must be raw, not DER.** ES256 is ECDSA over the P-256 curve with SHA-256. The signature is two numbers, `r` and `s`, 32 bytes each. JWS wants them plainly concatenated — 64 bytes. Many crypto libraries instead emit **DER**, a wrapper format that adds type-and-length headers, giving ~70 bytes. A DER signature in a JWT is rejected by every push service, and the error message won't tell you why. Cloudflare's WebCrypto returns raw 64 — this was verified before any of the code was written, because if it hadn't been, the whole approach would have needed rethinking.

**`sub` must be a `mailto:` or `https:` URL.** It's how a push service operator contacts you if your sender misbehaves. A bare email address is not valid; it needs the `mailto:` scheme.

## 4. Payload encryption — RFC 8291

Apple relays your notification. You don't want Apple reading "New contact submission from ada@example.com". So the payload is encrypted such that **only the subscribed device can decrypt it** — the push service is a blind courier.

This is the fiddliest part. It's four steps.

### Step 1 — ECDH: agree on a shared secret

**ECDH** (Elliptic Curve Diffie–Hellman) is a trick where two parties who have only exchanged *public* keys can compute the same secret number, and an eavesdropper who saw both public keys cannot.

You generate a **fresh, throwaway keypair for every single message** (called the "application server" key, `as_public` in the spec). Then:

```
your ephemeral private key  +  the device's p256dh public key  →  shared secret
the device's private key    +  your ephemeral public key       →  the same shared secret
```

Both sides land on the same 32 bytes. You send your ephemeral **public** key along with the message so the device can do its half.

Why fresh every time? If you reused one keypair and it leaked, every past message becomes readable. A new one per message limits the blast radius to that message.

### Step 2 — HKDF: turn the shared secret into real keys

The ECDH output is a shared secret, but it isn't uniformly random enough to use directly as an encryption key. **HKDF** (HMAC-based Key Derivation Function) is the standard way to stretch and clean up such a value.

HKDF takes three inputs and produces bytes:

- **IKM** (input keying material) — the raw secret
- **salt** — random or contextual bytes
- **info** — a fixed label that binds the output to a specific purpose

RFC 8291 runs HKDF **twice**:

```
1st:  IKM  = ECDH shared secret
      salt = the subscription's `auth` secret
      info = "WebPush: info" || 0x00 || device_public_key || your_ephemeral_public_key
      out  = 32 bytes  (call it IKM2)

2nd:  IKM  = IKM2
      salt = 16 fresh random bytes (sent with the message)
      info = "Content-Encoding: aes128gcm" || 0x00   →  16-byte content encryption key
      info = "Content-Encoding: nonce"     || 0x00   →  12-byte nonce
```

Those `info` strings are **exact**. A single wrong character produces different keys, encryption that looks completely successful, and a device that silently fails to decrypt. This is precisely the class of bug that a "did it return bytes?" test cannot catch — which is why this repo tests by actually decrypting (see §7).

The first HKDF mixing in `auth` is what ties the encryption to *this specific subscription*, not just to the keypair.

### Step 3 — AES-128-GCM: encrypt

**AES-128-GCM** is a symmetric cipher: same key encrypts and decrypts. GCM also produces an authentication tag, so tampering is detectable, not just unreadable.

Inputs: the 16-byte content encryption key, the 12-byte nonce, and your plaintext with a `0x02` byte appended (the "this is the final record" delimiter — `0x01` would mean more records follow).

### Step 4 — assemble the record

The bytes you actually POST are laid out like this:

```
┌──────────┬─────────┬────────┬──────────────────────┬──────────────┐
│ salt     │ rs      │ idlen  │ your ephemeral pubkey│ ciphertext   │
│ 16 bytes │ 4 bytes │ 1 byte │ 65 bytes             │ rest         │
└──────────┴─────────┴────────┴──────────────────────┴──────────────┘
```

The device parses this, pulls out your public key and the salt, redoes steps 1–2 from its side, and decrypts. Everything it needs is either in the record or already on the device.

`rs` is the record size (4096 here). `idlen` is the length of the key that follows — always 65 for P-256, because an uncompressed EC point is `0x04` followed by two 32-byte coordinates.

## 5. Sending

With the token and the encrypted body:

```http
POST https://web.push.apple.com/QF9x...
Authorization: vapid t=<the JWT>, k=<your VAPID public key, base64url>
Content-Encoding: aes128gcm
Content-Type: application/octet-stream
TTL: 86400
Urgency: normal

<the binary record from step 4>
```

`TTL` is how long the push service should hold the message if the device is offline. 86400 = one day. `TTL: 0` means "deliver now or drop it".

### Status codes that matter

| Code | Meaning | What this repo does |
|---|---|---|
| 201 | Accepted for delivery | Success |
| 400 | Malformed request | Log it — usually a bug in your headers |
| 401 / 403 | VAPID rejected | Check `aud`, `exp`, and that the key matches the subscription |
| 404 / 410 | **Subscription is permanently dead** | **Delete the row** |
| 413 | Payload too large | Keep payloads under ~4KB |
| 429 | Rate limited | Back off |

The 404/410 distinction is the one worth internalising. Those mean the subscription will *never* work again — the app was deleted, the browser dropped it, the endpoint rotated. Anything else may be transient. If you delete rows on any failure, one bad night at Apple silently unsubscribes every device you have, and nothing tells you.

## 6. How this repo puts it together

### Files

| File | Role |
|---|---|
| `Hono/src/worker/services/push/crypto.ts` | VAPID signing + RFC 8291 encryption. Pure functions, no I/O. |
| `Hono/src/worker/services/push/send.ts` | Fan-out to all devices, prune dead ones. Never throws. |
| `Hono/src/worker/routes/admin/push.ts` | subscribe / unsubscribe / devices / test. Behind the admin JWT guard. |
| `Hono/src/worker/db/migrations/2026-08-27_push_subscriptions.sql` | The one table. |
| `Hono/scripts/generate-vapid-keys.mjs` | Key generation. Prints only — writes nothing to disk. |
| `frontend/public/sw.js` | The service worker. `push` + `notificationclick`, nothing else. |
| `frontend/src/admin/hooks/usePushNotifications.ts` | Permission state machine, subscribe/unsubscribe. |
| `frontend/src/components/admin/NotificationsCard.tsx` | The dashboard UI. |

### Why there's no library

Every popular Node `web-push` library depends on Node's `crypto` module. Cloudflare Workers don't have it — they have **WebCrypto**, a different API. So the choice was a polyfill of unclear fidelity, or ~120 lines implementing the two RFCs directly against WebCrypto. The direct implementation won, after confirming every primitive existed in `workerd` first.

Two Workers-specific quirks are commented in the code where they bite:

- The ECDH parameter is `public` at runtime but Cloudflare's generated **types** call it `$public`. The code passes `public` with a cast, because the runtime is what matters.
- `crypto.subtle.exportKey` is typed as returning `ArrayBuffer | JsonWebKey`; only `"jwk"` gives the latter, so `"raw"` needs a cast.

### Why the service worker caches nothing

The usual PWA advice is to precache your app shell for offline use. This service worker deliberately has **no `fetch` handler at all**.

A CMS can't do anything useful without its API — offline support would buy "the app opens and then fails slightly more gracefully". Against that, a stale cached bundle running against a current API is a genuinely nasty bug, with no address bar to hard-refresh from in standalone mode.

Push requires a service worker. It does **not** require a caching strategy. Those are separate things, and this repo takes one without the other.

### Why failures can't break anything

Every trigger looks like this:

```ts
c.executionCtx.waitUntil(notify(c.env, { title, body, url, tag }));
return c.json({ success: true });
```

`waitUntil` tells the Worker runtime "keep running this after I've responded". So the contact form gets its `200` immediately and the push happens after. `notify()` also swallows all its own errors.

The reasoning: a stranger filling in your contact form must never see a 500 because Apple's push service was slow. The submission is already saved by that point — push is a courtesy layered on top, and courtesies don't get to fail the main thing.

### Degrading when unconfigured

With no VAPID secrets set, `isPushConfigured()` returns false and: the key endpoint reports `configured: false`, the dashboard card explains which secrets to set, and every trigger no-ops. Nothing throws. You can deploy this code with no secrets at all and the site behaves exactly as before.

## 7. How it was verified

Worth recording, because "it ran without error" would have been worthless here.

**The crypto is tested by decrypting.** A test worker encrypts with the shipped `crypto.ts`, then implements the *subscriber* side of RFC 8291 independently — parsing the record, redoing the ECDH and both HKDF passes from the device's private key — and checks the exact plaintext comes back. A wrong `info` string or swapped key order fails here, and would have looked perfectly healthy under any test that only checked that encryption produced output.

**The VAPID token is verified, not eyeballed** — signature checked against the public key, and `aud` asserted to be origin-only.

**Routes were exercised end to end** against a local Worker with a fake push service: subscribe, re-subscribe (must upsert, not duplicate — otherwise every launch adds a row and you get N copies of every notification), test send, 410 pruning, both public triggers, and a contact submission with the push endpoint killed mid-flight (still returned 200, row retained).

**Confirmed in production** (2026-08-27): after deploying, generating the VAPID keypair and setting the three secrets, enabling notifications on a real iPhone and using the card's **Send test** button delivered the notification through Apple's push service. So the full chain works — VAPID accepted, payload decrypted on-device, service worker woken, notification shown.

**Still not verified:** the campaign-finalisation trigger end to end. Exercising it would have sent live email through Resend to test addresses, so the code path is committed but has never run for real. The contact and newsletter triggers were verified locally against a fake push service, but not yet in production — submitting the live contact form is the cheap way to close that.

## Glossary

**AES-128-GCM** — A symmetric cipher (one key both encrypts and decrypts), with built-in tamper detection. The "128" is the key size in bits. Used for the notification payload.

**base64url** — A way of writing raw bytes as text, using only characters that are safe in URLs (`-` and `_` instead of `+` and `/`, no `=` padding). Every key and token here is base64url.

**CEK (Content Encryption Key)** — The 16-byte AES key derived by HKDF that actually encrypts the payload. Different for every message.

**DER** — A binary encoding format that wraps values with type and length headers. ECDSA signatures are often produced in DER; JWS requires them raw. Confusing these produces valid-looking but universally rejected tokens.

**ECDH (Elliptic Curve Diffie–Hellman)** — A method for two parties to derive the same shared secret having exchanged only public keys. An eavesdropper who saw both public keys cannot compute it.

**ECDSA** — Signing algorithm using elliptic curves. `ES256` = ECDSA + P-256 curve + SHA-256.

**Endpoint** — The URL, issued by a push service, that represents one subscription on one device. POSTing to it sends that device a push. Effectively a secret.

**Ephemeral key** — A keypair generated for a single use and discarded. Used per-message here so that a leak compromises only that message.

**HKDF** — HMAC-based Key Derivation Function. Turns a shared secret into one or more properly-formed keys, bound to a purpose by its `info` label.

**IKM (Input Keying Material)** — The raw secret fed into HKDF.

**JWS / JWT** — JSON Web Signature / Token. A signed `header.payload.signature` string, each part base64url. VAPID uses one to authenticate each send.

**Maskable icon** — An app icon with its important content inside the middle ~80%, so Android can crop it to a circle or squircle without cutting anything off.

**Nonce** — "Number used once." A 12-byte value that ensures encrypting the same text twice gives different ciphertext. Derived alongside the CEK, never reused with the same key.

**P-256** — The elliptic curve used throughout Web Push (also called `prime256v1` or `secp256r1`). A public key on it is 65 bytes: `0x04` then two 32-byte coordinates.

**Push service** — The vendor-operated server your device keeps a connection to. Apple, Google and Mozilla each run one. It relays your message; it cannot read it.

**PWA (Progressive Web App)** — A website with a manifest and a service worker that can be installed to a home screen and run like an app.

**RFC** — "Request For Comments." The numbered documents that define internet standards. RFC 8291 is the payload encryption spec; RFC 8292 is VAPID; RFC 8188 defines the `aes128gcm` content encoding they build on.

**Salt** — Random bytes mixed into key derivation so the same inputs don't always produce the same keys. Sent in the clear with the message; it isn't secret, it's for uniqueness.

**Scope (service worker)** — The URL prefix a service worker controls. `/admin` here, so the public site has none.

**Service worker** — A script the browser can run with no page open. Required for push, because there's no page to deliver to.

**Standalone** — Display mode where an installed web app runs without browser chrome — no address bar, no tabs.

**Subscription** — The `{endpoint, p256dh, auth}` triple identifying one device. Created in the browser, stored on your server.

**TTL** — How long a push service should hold an undelivered message before dropping it. Seconds.

**VAPID** — Voluntary Application Server Identification. The keypair-and-JWT scheme proving to a push service that a send came from you.

**WebCrypto** — The browser/Worker-standard crypto API (`crypto.subtle`). Different from Node's `crypto` module, which is why Node push libraries don't work on Workers.

**`waitUntil`** — Worker runtime method meaning "keep this promise running after I've sent the response". How push is sent without delaying the user's request.
